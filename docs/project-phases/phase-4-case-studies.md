### Context

Learning and Development work at a live hotel property includes recurring programmes, compliance activity, templates, reporting and handover between people. The information required to complete that work had been distributed across six separate knowledge sources. `[NEEDS INPUT: identify the six source types without disclosing confidential information]`

This created a practical documentation problem. A person completing a recurring task could need to locate several references, remember where an earlier decision had been recorded or rely on knowledge passed from one colleague to another. `[NEEDS INPUT: confirm which of these conditions existed and provide one safe example]`

My task was to bring the available material into one reference that could support day-to-day work. I was not redesigning the complete L&D strategy, setting policy or replacing formal Marriott standards. The scope was to organise the operating knowledge available to the property-level function.

### Challenge

The visible problem was fragmentation. The deeper problem was deciding what belonged together, what needed to remain separate and how another person would find the correct instruction at the moment of use.

A long document could solve the storage problem while creating a new navigation problem. The manual therefore needed more than accumulated content. It needed a structure that reflected recurring work and made the relationship between standards, templates and action clear.

Three questions shaped the work:

1. What does the L&D operator need to know before beginning a recurring task?
2. Which source is authoritative when two references appear to overlap or disagree?
3. What should be documented in the manual, and what should remain in a separate working file or formal company system?

### What I would do differently

#### 1. Design the maintenance model before expanding the document

A 150-page manual can become difficult to maintain if every type of information is treated in the same way. Stable standards, changing procedures, working templates and temporary programme details have different update cycles.

In a next iteration, I would divide the system into three layers:

- A concise operating guide for stable decisions and responsibilities.
- A linked template library for files used in recurring work.
- A change log with a named owner, review date and version history.

This would make the system easier to update without requiring the full manual to be reviewed every time one working file changes.

#### 2. Test retrieval, not only completeness

The page count proves effort, not usability. A complete document still fails if another person cannot find the right answer quickly.

I would ask a colleague unfamiliar with the manual to complete three recurring tasks using only the guide. I would record where they stopped, what they searched for and which labels did not match their language. The results would inform the next navigation and naming revision.

#### 3. Define adoption evidence at launch

The original evidence plan did not produce a reliable measure of use or effect. In a next version, I would define a small measurement set before release:

- Number of recurring tasks supported by the manual.
- Number of users who accessed it during the first 30 days.
- Task-completion questions or errors raised after use.
- Sections most frequently updated or clarified.
- User rating of findability after completing a real task.

This would allow the next case study to report whether the manual changed the work, not only whether it was completed.

### Context

The Digital Learning Zone assigns learning according to role and function. When an associate changes position, the learning path attached to the earlier role may no longer reflect the work they are expected to perform.

The reported scope covered [NEEDS INPUT: confirm 19] associates whose positions had changed. The task was to review the available role information, identify an appropriate learning path and update or recommend the required assignment. `[NEEDS INPUT: confirm the exact system action and approval process]`

This was an administrative task with a judgement problem inside it. A role title alone may not contain enough information to support a reliable mapping. Assigning a path without resolving that ambiguity could create inaccurate learning records or irrelevant learning requirements.

### Challenge

The task required consistency without pretending that every case was clear.

The main risks were:

- Mapping an associate to a path based only on an incomplete title.
- Applying different logic to similar roles.
- Updating an assignment without recording why the decision was made.
- Treating a clean spreadsheet as proof that the underlying role data was correct.

### What I would do differently

#### 1. Define the decision rules before reviewing individual cases

If mapping logic develops row by row, similar roles can receive different treatment. In a next iteration, I would agree a short decision framework before beginning:

- Which role source is authoritative?
- Which differences require a new learning path?
- Which cases can be decided by L&D?
- Which cases require department-head confirmation?
- What evidence must be retained for the decision?

This would improve consistency and make the process easier to review.

#### 2. Record exception reasons and effective dates

A simple status such as `mapped` or `pending` does not explain why a case was difficult. I would add reason codes for common exceptions, an effective date and a named decision owner.

That would make repeated ambiguity visible. It could also reveal whether the real problem lies in the learning catalogue, the role data or the handover process when a position changes.

#### 3. Add a post-update audit

The current evidence ends at the mapping activity. In a next iteration, I would review the system 30 days after the update and check:

- Whether the intended path was assigned.
- Whether obsolete learning remained attached.
- Whether the associate could access the required learning.
- Whether new ambiguous cases appeared.
- Whether completion reporting reflected the new role correctly.

This would connect the mapping decision to system quality rather than treating spreadsheet completion as the finish line.

#### 4. Bring department confirmation earlier

Where role information is unclear, late escalation slows the update. I would ask department representatives to confirm the role list and decision owner before mapping begins. This would reduce avoidable rework while preserving the rule that L&D should not guess.

### Context

Marriott Culture Week 2026 was a property-wide programme reported as running across [NEEDS INPUT: confirm five] days. My reported contribution covered activity design, MC scripts, certificates, awards coordination and digital content. `[NEEDS INPUT: confirm each responsibility and identify collaborators]`

The strongest surviving artifact is Obstacle Challenge, created for Day 2 at The Westin Resort & Spa Cam Ranh. The HTML file identifies the session as taking place in Ballroom A on Tuesday, 14 July at 10:30 AM. `[NEEDS INPUT: confirm that these published artifact details match the event as delivered]`

The challenge was to turn culture content into an activity that could hold attention in a shared room, give multiple teams repeated opportunities to participate and remain controllable by an MC from one screen.

### Challenge

A culture event can become passive when the audience only listens. It can also become confusing when a game has too many rules, unclear scoring or no reliable operator view.

Obstacle Challenge needed to support two users at once:

- The teams, who needed clear rules, time pressure and visible progress.
- The MC, who needed to open questions, run the timer, reveal answers, record scores and move the room through the activity.

The experience also needed to work as a projected interface rather than an individual mobile activity. That affected type size, control placement, pacing and the amount of information shown at one time.

### What I designed

I created a working browser-based crossword race with ten clues across and one hidden ten-letter keyword down.

The artifact includes:

- Four colour-coded teams.
- Ten clue rows and a hidden golden column.
- A rule that every team answers every clue.
- A 20-second timer for each question.
- Ten points for each correctly spelled answer.
- One Hope Star decision per team, worth 20 points when correct and minus 10 when wrong.
- A 50-point hidden-keyword attempt activated by ringing a bell.
- Elimination from further play after an incorrect keyword attempt.
- Operator controls to start, pause, reveal and close questions.
- Score, results and final recognition screens.
- A published sequence from title, rules and game board to results.

These mechanics are verified from the supplied HTML artifact. They describe the product as built, not the participant response or learning effect.

### How I ran it

The designed facilitation flow was:

1. Introduce the four teams and explain the shared-answer format.
2. Allow teams to select clues in turn.
3. Give every team 20 seconds to write an answer.
4. Ask teams to reveal answers together on the MC's count.
5. Record the score and reveal the correct answer.
6. Allow each team one declared Hope Star decision on its own clue.
7. Keep the hidden keyword available as a high-risk attempt during the round.
8. Close with the final results and recognition message.

### What I would do differently

#### 1. Reduce the rule load before the first question

The game combines shared answers, exact spelling, turn order, a Hope Star decision, a hidden keyword, a bell and elimination. These mechanics create energy, but they also increase the amount the MC must explain and monitor.

In a next iteration, I would test the rules with a small group before the event and remove any mechanic that does not improve the learning objective. I would also place a one-screen rule summary beside the board so teams do not need to remember every condition after the introduction.

#### 2. Build an operator rehearsal and fallback plan

The interface was designed for a live room, where hesitation is visible. A missed score, timer error or display problem can interrupt the experience.

I would create:

- A five-minute operator rehearsal.
- A one-page MC guide with the exact control sequence.
- A printed answer and scoring sheet.
- A static slide fallback if the browser or projector fails.
- A reset procedure that does not erase confirmed scores.

This would reduce the amount of judgement required from the operator during the live activity.

#### 3. Measure the learning objective, not only the result board

The current product records game performance, but game score is not the same as culture understanding.

In a next iteration, I would define one learning objective for the round and add a short post-activity check. This could include three scenario questions, one team reflection or a manager observation prompt used after Culture Week.

The case could then report recall, application or discussion quality rather than only participation and points.

#### 4. Improve accessibility and technical weight

The supplied artifact uses colour-coded teams, animated effects, emoji and large embedded image data. It was made for projection, but the same choices make the file heavier and can reduce accessibility.

I would:

- Pair every team colour with a visible team name and pattern.
- Replace emoji-only meaning with labelled controls.
- Confirm full keyboard operation for the MC.
- add a reduced-motion mode to every animated state.
- Compress or separate large image assets and keep an offline package.
- Test contrast on every projected screen state.

This would make the product easier to operate, more portable and safer to reuse.
